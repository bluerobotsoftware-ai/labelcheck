# Sample labels

Eleven PNGs in `public/samples/`, generated by `scripts/make-samples.ts` (`npm run samples`),
plus `public/samples/manifest.json` describing each one.

## Why these are drawn, not photographed

A reviewer opening the deployed app needs something to test with immediately, and a demo is
only worth anything if the right answer is known in advance. Real bottle photographs give us
neither: sourcing them is slow, and nobody can say authoritatively what verdict a given photo
*should* produce.

So the artwork is deterministic vector drawing rasterised to PNG. We control exactly which
defects exist, which means every sample has a known expected verdict — recorded in the
manifest and asserted by the generator itself. Regenerating produces byte-identical output,
so a rerun yields an empty diff unless the artwork genuinely changed.

That makes the set serve double duty: a demo fixture list, and a regression oracle for
`src/lib/ttb/rules.ts`.

## What the manifest gives you

Each entry carries three distinct things, and the distinction matters:

| Field | Meaning |
|---|---|
| `application` | The typed-in half of the COLA — what the applicant claims. |
| `labelText` | Ground truth for what the artwork actually prints. `null` means *deliberately absent*. |
| `expected` | The verdict a correct implementation must reach, per check id plus an overall recommendation. |

`labelText` is the useful one for testing the vision extractor: extraction accuracy can be
scored against it without a human re-reading the images. Check ids in `expected.checks`
correspond to `CheckResult.id` in the rules engine.

The manifest also carries `canonicalWarning`, the 27 CFR 16.21 text verbatim, so the rules
engine and the fixtures cannot drift apart on what the mandated wording is.

## The eight base labels

| File | Type | Planted defect | Expected |
|---|---|---|---|
| `spirits-bourbon-compliant.png` | Spirits | none | **approve** |
| `wine-compliant.png` | Wine | none | **approve** |
| `malt-compliant.png` | Malt | none | **approve** |
| `malt-case-and-apostrophe-variant.png` | Malt | case + apostrophe variance | **approve** |
| `spirits-abv-mismatch.png` | Spirits | `abv-mismatch` | **reject** |
| `wine-warning-title-case.png` | Wine | `warning-header-not-capitalised` | **reject** |
| `malt-warning-wording.png` | Malt | `warning-text-altered` | **reject** |
| `spirits-missing-net-contents.png` | Spirits | `net-contents-missing` | **reject** |

### 1. `spirits-bourbon-compliant.png` — approve

Old Tom Distillery, Kentucky Straight Bourbon Whiskey, 45% Alc./Vol. (90 Proof), 750 mL,
bottler line, warning verbatim. Every application field appears on the artwork.

This is the reference label and the parent of all three degraded variants, so it is
deliberately kept clean: no case variance, no format variance, nothing borderline.

### 2. `wine-compliant.png` — approve

Hollow Creek Vineyards, Napa Valley Cabernet Sauvignon, 2021.

Carries one thing worth noticing: the label prints `ALCOHOL 13.5% BY VOLUME` while the
application records `13.5% Alc./Vol.`. That is a **formatting difference, not a defect**. A
correct implementation normalises both to `13.5` and passes. An implementation that string-
compares will fail this and be wrong.

### 3. `malt-compliant.png` — approve

Iron Kettle Brewing, India Pale Ale, 6.8% ALC/VOL, 12 FL OZ (355 mL).

Reversed out of a dark green ground, so it also exercises extraction from light-on-dark
artwork rather than dark ink on pale stock. Class/type is printed in capitals against a
title-case application value, which must still pass.

### 4. `malt-case-and-apostrophe-variant.png` — approve (trap)

The artwork sets the brand as `STONE’S THROW` in display capitals with a typographic
apostrophe (U+2019). The application types `Stone's Throw` in title case with an ASCII
apostrophe (U+0027).

**This must pass.** It differs only by letter case and apostrophe codepoint, and a correct
implementation case-folds and unicode-normalises before comparing. Flagging it as a mismatch
is a false positive, and it is the single most likely defect in a naive implementation —
which is exactly why it is here. The bottler line carries the same variance.

The generator asserts, at build time, that the two strings really do differ in raw bytes and
really are identical after folding. If that assertion ever stops holding, the sample has
stopped testing what it claims to test.

### 5. `spirits-abv-mismatch.png` — reject

Application declares 45% Alc./Vol. (90 Proof); the label prints 40% Alc./Vol. (80 Proof).

The label is *internally consistent* — the proof figure agrees with its own percentage — so
nothing about the label alone looks wrong. Only comparison against the application catches
it. Five percentage points is far outside the 0.15 point tolerance for distilled spirits
(27 CFR 5.65).

Expected: `alcohol-content` fails, everything else passes.

### 6. `wine-warning-title-case.png` — reject

Every field matches and the warning wording is verbatim, but the mandated header is set as
`Government Warning:` rather than `GOVERNMENT WARNING:`.

The interesting property: **a word-level diff of the warning text shows no difference at
all.** The defect lives purely in letter case, which is why header capitalisation has to be
its own check rather than falling out of a text comparison.

Expected: `government-warning-header-caps` fails, `government-warning-text` passes.

### 7. `malt-warning-wording.png` — reject

Header is correct; the wording is altered in two places:

- `women should not drink` → `women should avoid drinking`
- the closing clause `, and may cause health problems` is dropped from statement (2)

The warning is prescribed verbatim, so any substitution or omission fails. This is the
sample to use when demonstrating the word-level warning diff, because it contains one
substitution *and* one deletion.

Expected: `government-warning-text` fails, header capitalisation passes.

### 8. `spirits-missing-net-contents.png` — reject

The application declares 750 mL; the artwork carries no net contents statement anywhere.

The alcohol statement is centred rather than left in a two-up row, so nothing looks
conspicuously absent — the omission has to be found by *reading* the label, not by spotting
a gap. This is the sample that separates "field absent" from "field unreadable": the image is
clean, so the correct verdict is `fail`, never `unreadable`.

One subtlety worth flagging, because the domain model calls it out: net contents are
frequently embossed into the glass rather than printed, so a label with no printed net
contents is not automatically a failure. This application deliberately leaves
`containerInfoNotOnLabels` unset — nothing is declared as blown, branded or embossed — so
that escape hatch does not apply here and the omission is a genuine failure.

Also exercises an ampersand in the brand name (`JUNIPER & THORNE`).

## The three degraded variants

All derived from `spirits-bourbon-compliant.png`, to test image robustness rather than
compliance logic. The application data is identical in each case; only image quality differs.

### `spirits-bourbon-compliant--rotated-8deg.png` — approve

Rotated 8 degrees onto a grey ground, then scaled to a 1000px long edge. Everything stays
legible, so **rotation must not change any verdict**. Expect the same approval as the parent,
with a rotation noted under image quality.

### `spirits-bourbon-compliant--glare.png` — approve

Two white radial-gradient ellipses composited over the artwork, as from a phone flash on a
glossy bottle.

Composited with an `over` blend rather than `screen`: the stock is already near-white cream,
and screening white onto cream is very nearly a no-op — the first attempt at this sample was
too subtle to test anything. Painting semi-opaque white actually destroys local contrast, the
way a real reflection does.

`DISTILLERY` and part of the class/type wash out to low contrast but stay readable, and the
small print at the foot is untouched. No mandatory field is obscured, so this should still
approve, with a glare note under image quality.

### `spirits-bourbon-compliant--blurred-underexposed.png` — needs_review

Gaussian blur at sigma 2.6, brightness halved, contrast reduced.

Tuned so that the brand and class/type survive but the government warning small print does
not resolve. **This is the sample that should exercise the `unreadable` path** — the correct
behaviour is to decline to judge the warning, not to guess at it and not to fail it. A
system that returns `pass` here is hallucinating text it cannot see; one that returns `fail`
is punishing an applicant for a bad photograph.

Expected: warning checks and the bottler line come back `unreadable`, image quality fails,
and the overall recommendation is `needs_review`.

## Implementation notes

**Fonts.** The deployed environment has no custom fonts, so every font stack ends in a
generic family. Note that a bare generic on its own is *not* safe: on some fontconfig setups
(including the Windows box this was authored on) bare `serif` resolves to a **monospace**
face, which makes labels look like wireframes. Naming real faces first and falling back to
the generic gives good typography where those faces exist and a sane serif/sans elsewhere.

**Text layout.** SVG has no automatic wrapping and librsvg does not support `<foreignObject>`,
so wrapping is done in the generator. Widths are not estimated — they are measured with
libvips' Pango text renderer at 72 dpi, calibrated against real librsvg output to within 0.5%.
Two wrinkles that cost time and are worth knowing: Pango refuses to measure whitespace on its
own (`no text to render`), so a space is measured by difference against anchor glyphs; and it
parses its input as Pango markup, so a literal `&` must be escaped or measurement throws.

**Palettes.** One visual family per beverage type — parchment and oak for spirits, ivory and
burgundy for wine, a dark ground with gold for malt — with a per-sample accent shift so that
four spirits labels do not look like one label four times.

**File size.** Anything over 200 KB is re-encoded with a 256-colour palette. These are flat
vector designs in a handful of hues, so quantisation is visually lossless (measured mean
channel delta on the worst case, the rotated variant, is 0.03/255) while cutting that file
from 372 KB to 109 KB. The generator asserts a hard 400 KB ceiling per file.

**Self-checks.** The generator does not merely describe its defects in the manifest, it
asserts they are actually present in the output: that the ABV strings really differ, that the
title-case header differs *only* in case, that the reworded warning contains the substitution
and lacks the dropped clause, that the missing field is really null, and that every compliant
sample carries the canonical warning verbatim. Each assertion is capable of failing; a green
run means the fixtures really do test what this document claims.
